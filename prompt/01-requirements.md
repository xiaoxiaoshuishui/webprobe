## 1.1 用户指令（原文）

> 阅读项目要求文档。针对虎牙直播（浏览器端）实现一个软件测试平台
> —— 附带文件 `D:\qq\File\FileRecv\软件安全小项目.pdf`

## 1.2 读取 PDF 的过程

第一步尝试直接读取 PDF，得到 `cannot read ...: binary file`——说明需要先做文本抽取。
环境中没有任何 PDF 库（`pypdf` / `pymupdf` / `pdfminer` 均不存在），且 `pip install`
在该环境下挂起，因此**没有走"装库"这条路，而是自己写了一个零依赖的 PDF 文本抽取器**。

产生了两版：

1. **第一版 `tools/pdf_extract.py`**：正则扫描所有 `stream ... endstream`，对含
   `FlateDecode` 的做 zlib 解压，再抓 `Tj`/`TJ` 操作符。
   **结果失败**——输出 500KB 乱码。根因是字体嵌入流（font file stream）中也含有
   字节序列 `BT`/`Tj`，启发式过滤把字体二进制当成了内容流。

2. **第二版 `tools/pdf2txt.py`**：改为**解析对象图**——先按 `N G obj ... endobj`
   建立对象表，再找 `/Type /Page` 对象，取 `/Contents` 指向的真实内容流解压，
   并解析 `/Resources /Font` 下的 `/ToUnicode` CMap 处理 CID 字体。

   **第一次运行仍然不理想**：每个汉字一行。根因是该 PDF 每个字形都用独立的
   `Td` 定位，而初版实现把**每一次 `Td` 都当作换行**。

   **修正**：跟踪文本矩阵的 y 坐标，只有 y 变化超过 `0.3 × fontsize` 时才换行；
   同一行内根据 x 累计位移插入空格。修正后得到干净的三页文本。

## 1.3 抽取出的需求（原文要点）

> **关于学期末的小项目**
>
> 你需要利用任何一款大模型实现一个软件测试平台，并开源到 GitHub 上。
>
> - 软件测试平台的**输入**：待测软件所在的**目录**
> - 软件测试平台的**功能**：**动态执行**该软件并且在**崩溃错误发生时捕获**下来
> - 软件测试平台的**输出**：在待测软件中找到的 **bug**
>
> **开源的项目目录结构如下：**
> - `readme.md` —— 介绍如何使用你的平台
> - `code*` —— 存放软件测试平台的代码的文件夹
> - `video*` —— 存放你成功运行软件测试平台对任意软件进行测试的录像的文件夹
> - `prompt*` —— 存放你和大模型交互产生该软件测试平台并调试的完整对话过程的文件夹
>
> 你可以参考这里：`https://github.com/jinglingsun/android-testing-platform`

## 1.4 对需求的解读（这一步决定了整个架构）

| 需求条目 | 解读 | 落地方式 |
| --- | --- | --- |
| 输入 = 待测软件所在目录 | **是目录，不是 URL** | 平台以"目录 + `target.json` 清单"为输入单位；本地 Web 应用由平台自带的静态服务器托管后执行 |
| 功能 = 动态执行 | 必须真的把它跑起来 | 启动真实 Chromium，导航、点击、输入、提交、滚动、悬停、键盘模糊测试 |
| 功能 = 崩溃错误发生时捕获 | 捕获是**事件驱动**的，不能只做静态检查 | 同时挂 4 类来源：Playwright 页面事件、CDP 域事件、注入页面的 `error`/`unhandledrejection` 监听、主动探测 |
| 输出 = 找到的 bug | 需要**可复现、可取证**，不是一句结论 | 每个缺陷都带截图、DOM 快照、控制台日志、网络记录、复现步骤、可执行复现脚本 |
| 开源到 GitHub | 需要完整仓库结构 | `readme.md` / `code/` / `video/` / `prompt/` + `LICENSE` + `.gitignore` + git 历史 |
| `video*` 存放运行录像 | **录像本身也是交付物**，要能看懂 | 平台用 CDP screencast 自己录，并把状态面板、实时缺陷清单、元素高亮与开场/结尾卡**画进被测页面**，使录像不必对照终端即可读懂（这一条是被**使用者反馈**倒逼出来的，见 `04-debug-log.md` 的 D-19） |
| 参考 android-testing-platform | 那是 Android 端动态测试 | 本项目是**浏览器端**的对应物：同思想（驱动器 + 事件捕获 + 报告），不同平台 |

## 1.5 针对"虎牙直播（浏览器端）"的额外要求

用户额外指定了被测对象，因此平台必须**能真的测一个生产环境的网站**，而不只是玩具样例。
这带来了三条硬约束，贯穿后续所有设计：

1. **必须能处理真实站点的体量与噪声**（4000+ 请求、几十个第三方域名）；
2. **必须能区分"被测站点自身的缺陷"与"它内嵌的第三方广告/统计组件的缺陷"**；
3. **绝不能做破坏性操作**（不能点退出登录、支付、删除），也不能把时间预算耗在视频拉流上。

这三点直接催生了 `firstPartyDomains` / `watch.thirdParty` 策略、`allowDestructive=false`、
以及 `explore.urlPatterns` 白名单机制。
