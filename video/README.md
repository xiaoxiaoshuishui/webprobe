## 录像里能看到什么

录像不是"浏览器自己逛网页"的沉默演示——**平台的结论被直接画在被测页面里**，
所以不需要对照终端或报告文件也能看懂：

| 时间 | 画面 | 内容 |
| --- | --- | --- |
| 0:00–0:05 | **开场信息卡** | 被测目标、入口地址、目标目录、页面/动作/时长预算、随机种子、浏览器与视口 |
| 0:05–5:00 | **状态面板**（每个页面左下角） | 已运行时长；当前动作（如 `▶ [25/35] 悬停 …`）；`页面 6/10 动作 73 请求 4000（失败 95） 缺陷 24`；**实时缺陷清单**（按严重级配色，带类型与出现次数） |
| 同上 | **元素高亮** | 一条红色虚线框 + 缺陷标题，直接框在出问题的元素上，让"bug 在哪儿"可见 |
| 5:00–5:14 | **结尾结果卡** | 共发现 25 个缺陷；严重级分布（中 3 · 低 22）；第一方/第三方归属；执行规模；**Top 10 缺陷清单**（编号 + 严重级 + 类型 + 标题）；完整报告路径 |

界面采用深色主题，面板半透明且不遮挡关键内容（`pointer-events: none`，模糊测试点不到它）。

## 录像是怎么产生的

不是人工录屏，而是**平台自己录的**：`code/src/core/recorder.mjs` 使用 Chrome DevTools 协议的
`Page.startScreencast` 域抓取 JPEG 帧，**每一帧都带有它产生的时刻**，
再用 ffmpeg 的 concat demuxer 按这些时间戳设定每帧的显示时长。

因此录像的播放速度与真实的测试速度一致，而不是按猜测的固定帧率拼出来的。
两处必要的处理（细节见 `prompt/04-debug-log.md` 的 D-20 / D-21）：
按约 10fps 节流，避免 4000 帧上限把录像截断在结尾卡之前；
最后一帧的时长取真实停止时刻，保证结果卡停留多久就播放多久。

## 复现这次运行

```bash
node code/src/cli.mjs run --target code/targets/huya-live
```

可用的相关开关：

```bash
# 调整开场/结尾卡停留时长（秒），0 = 不显示
node code/src/cli.mjs run -t code/targets/huya-live --intro 6 --outro 20

# 关掉页内叠加面板（录像将只剩下页面本身）
node code/src/cli.mjs run -t code/targets/huya-live --no-hud
```
